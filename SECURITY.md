# Security

## Reporting a vulnerability

Please open a private security advisory on the GitHub repository (Security tab) instead of a public issue. Include the version, a description, and steps to reproduce.

## Threat model

BackupVouch handles database credentials, storage credentials, and copies of production data. The main risks and the planned mitigations:

| Risk | Mitigation |
|---|---|
| Credentials leak through logs, events, or status | Secrets are only referenced by name and injected into Jobs as environment variables from `secretKeyRef`. The operator never reads Secret values. The runner never prints them. |
| A verification run exposes production data | The scratch Postgres runs inside the verification Job's own container, with data on an `emptyDir`. Nothing is exposed on the network. |
| Verification Job reaches other services | Recommended NetworkPolicy: allow egress only to the storage endpoint and DNS. |
| Over-privileged operator | RBAC limited to what the controller needs (table below). It does not read Secrets. |
| Compromised container escalates | Jobs run as a fixed non-root UID, with a read-only root filesystem (writable `emptyDir` mounts only), no privilege escalation, all capabilities dropped, the `RuntimeDefault` seccomp profile, no service account token (`automountServiceAccountToken: false`), and resource limits. |
| A BackupPolicy author runs an arbitrary image or reads other Secrets | `runnerImage` must match the operator's allow-list (default: only its own image, D14). Without it, creating a BackupPolicy would equal permission to run any image with any Secret of the namespace. |
| Stored backups are deleted by a stolen credential | Prune and backup Jobs need delete rights on the bucket. Use a bucket or prefix scoped credential, and enable bucket versioning or object lock where you can. |
| Check results leak data into status | Messages never contain Secrets or row data; the actual value is echoed only for short booleans and numbers (`docs/ARCHITECTURE.md`). Pod logs may contain data, so restrict `pods/log`. |
| Malicious SQL in checks | Checks are written by whoever can create a BackupPolicy. They run only against the throwaway restored copy, never the source database, inside a read-only transaction with a statement timeout. Treat permission to create BackupPolicies as sensitive. |
| Tampered or truncated backup | The runner records a SHA-256 on upload and verification refuses a mismatch. |
| Source database is damaged by backup load | The dump uses a read-only role. Backup Jobs have timeouts and resource limits. |

## Operator RBAC

| Resource | Verbs | Why |
|---|---|---|
| backuppolicies | get, list, watch, update, patch | main reconcile object, adding and removing the finalizer |
| backuppolicies/finalizers | update | needed to set owner references that block deletion when the cluster enforces owner reference permissions |
| backuppolicies/status | get, update, patch | report results |
| jobs (batch) | get, list, watch, create, delete | run backup and verification Jobs, clean up |
| pods | get, list, watch | read the termination message of Job pods |
| events (events.k8s.io group) | create, patch, update | emit events through the `events.k8s.io` recorder (`mgr.GetEventRecorder`); a rule on the core `events` resource would not apply (VERIFY on a cluster in the e2e run) |
| tokenreviews, subjectaccessreviews (authentication and authorization groups) | create | protect the metrics endpoint, generated by the kubebuilder scaffold |
| leases (coordination.k8s.io) | get, list, watch, create, update, patch, delete | leader election |

No access to Secrets, nodes, or anything cluster-wide beyond this. There is no `update` or `patch` on Jobs (they are never modified, only created and deleted) and no write access to Pods. The runner Jobs themselves need no Kubernetes API access at all, which is why they get no service account token.

The scaffold also generates `backuppolicy_admin_role`, `backuppolicy_editor_role` and `backuppolicy_viewer_role`. Grant them deliberately: whoever can create a BackupPolicy chooses SQL that runs on a restored copy of production data and chooses which Secrets of the namespace the Jobs use.

## Recommended hardening for users

- Give BackupVouch a dedicated read-only database role for dumps.
- Use storage credentials limited to one bucket or prefix.
- Apply the egress NetworkPolicy from `docs/ARCHITECTURE.md`. It is a recommendation, BackupVouch does not create it, so nothing enforces it unless you do.
- Set the allow-list of runner images on the operator and keep it narrow.
- Pin the runner image by tag or digest.

### Recommended NetworkPolicy for Verification Jobs

Verification Jobs (`backupvouch.pages.dev/role: verify`) only need egress to Kubernetes DNS and the S3 storage endpoint; they never connect to the source database:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backupvouch-verify-egress
  namespace: default
spec:
  podSelector:
    matchLabels:
      backupvouch.pages.dev/role: verify
  policyTypes:
    - Egress
  egress:
    # Allow DNS resolution
    - to:
        - namespaceSelector: {}
          podSelector:
            matchLabels:
              k8s-app: kube-dns
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
    # Allow egress to S3 storage endpoint (your in-cluster S3 service)
    - to:
        - podSelector:
            matchLabels:
              app.kubernetes.io/name: s3
      ports:
        - protocol: TCP
          port: 8333
```

## Status dashboard

Off by default (`--dashboard-bind-address`, D21). When on, it is unauthenticated and read-only: GET and HEAD only, no writes, no new RBAC (it reads BackupPolicies through the existing cache). It shows policy names, namespaces, schedules, backup object keys, sizes, checksums and failure messages; it never shows hosts, buckets or Secret names. The recommended setup binds `127.0.0.1` and uses `kubectl port-forward`. A strict Content-Security-Policy allows only same-origin files, there is no inline script, and the page builds the DOM with text nodes only (a test forbids `innerHTML`). Anyone who can reach a non-loopback listener can read the status, so put it behind an authenticating proxy if you expose it.
