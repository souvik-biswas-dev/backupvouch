# INSTALL

Status: step 7. The install manifest is generated by `make build-installer` and was rendered with a real kustomize while writing this step. Applying it to a cluster was not tested yet, apart from the e2e script that deploys the same kustomization (`make deploy`). No release exists yet, so the "install from a release" command below only works after the first release is published.

## What you need

- A Kubernetes cluster and `kubectl`.
- An S3-compatible object store (the demo uses SeaweedFS; any S3 server works) with a bucket, and a Secret with its access key.
- A PostgreSQL 16 source database and a Secret with a (preferably read-only) role. Other major versions need another runner image, see `DECISIONS.md` D15.

## Install the operator

From a release (after the first release exists):

    kubectl apply -f https://github.com/souvik-biswas-dev/backupvouch/releases/download/v0.1.0/install.yaml

Or build the manifest yourself from a checkout:

    make build-installer              # writes dist/install.yaml, operator image ghcr.io/souvik-biswas-dev/backupvouch:v0.1.0
    make build-installer IMG=registry.example.com/backupvouch:v0.1.0   # your own registry
    kubectl apply -f dist/install.yaml

`make build-installer` refuses an image without a tag or with `:latest`, and checks that the finished file contains no `:latest` image. It prints the operator image and the default runner image it used. It does not leave `config/manager/kustomization.yaml` modified.

The manifest creates the namespace `backupvouch-system`, the CRD, RBAC, the metrics Service and the Deployment. The operator watches BackupPolicies in all namespaces. The Jobs it creates run in the namespace of the BackupPolicy, and the Secrets named in a policy must exist in that namespace.

The images (`ghcr.io/souvik-biswas-dev/backupvouch` and `...-runner`) are published by `.github/workflows/publish-images.yml` when a tag `vX.Y.Z` is pushed. New packages on ghcr.io are private by default: make them public in the GitHub package settings, or clusters cannot pull them without an image pull secret.

## Create your first BackupPolicy

    kubectl create secret generic pg-creds    --from-literal=username=backupvouch_ro --from-literal=password=...
    kubectl create secret generic s3-creds --from-literal=accessKey=...           --from-literal=secretKey=...
    kubectl apply -f config/samples/backup_v1alpha1_backuppolicy.yaml
    kubectl get backuppolicies               # short name: bp

`config/samples/demo/` has a complete, working set (an S3 store, a seeded Postgres, a policy) for a throwaway cluster, and `make demo` runs it, see `TESTING.md`. The field reference is `API.md`.

## Runner images and `--allowed-runner-images`

Every backup, verification and prune Job runs the runner image. Letting a policy author pick any image would let them run any code with the policy's Secrets mounted, so the operator limits it (D14):

- Without a setting, a policy may use only the operator's default runner image (`ghcr.io/souvik-biswas-dev/backupvouch-runner:v0.1.0` for this release) or leave `spec.runnerImage` empty.
- `--allowed-runner-images` takes a comma-separated list of exact image names or glob patterns. The match uses Go's `filepath.Match`: `*` matches any run of characters except `/`, `?` matches one character, `[a-z]` a range. So `registry.example.com/team/*` matches `registry.example.com/team/runner:v1` but not `registry.example.com/team/sub/runner:v1`.
- A policy with an image that matches nothing gets `SpecValid=False` with reason `RunnerImageNotAllowed`, and no Job is started.

Set it with a kustomize overlay, which survives upgrades:

```yaml
# kustomization.yaml
resources:
  - dist/install.yaml
patches:
  - target:
      kind: Deployment
      name: backupvouch-controller-manager
    patch: |-
      - op: add
        path: /spec/template/spec/containers/0/args/-
        value: --allowed-runner-images=registry.example.com/team/*,registry.example.com/other/runner:v2
```

or on a running cluster (the Pod restarts):

    kubectl -n backupvouch-system patch deployment backupvouch-controller-manager --type=json \
      -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--allowed-runner-images=registry.example.com/team/*"}]'

Prefer exact, pinned names over wide patterns, and never allow a registry path that others can push to.

## Metrics

The manager serves Prometheus metrics over HTTPS on port 8443, protected by Kubernetes authentication and authorization. A scraper needs a token that is allowed to `get` the `/metrics` URL (the `metrics-reader` ClusterRole in the manifest grants that). The four metrics are listed in `ARCHITECTURE.md`. A ServiceMonitor and a NetworkPolicy exist as overlays in `config/prometheus` and `config/network-policy` but are not enabled in the default install.

## Network policy

BackupVouch does not create NetworkPolicies for the Jobs. Apply the egress policy recommended in `SECURITY.md` and `ARCHITECTURE.md`: verification and prune Jobs need only DNS and the object store.

## Upgrade

Apply the new `install.yaml`. It updates the CRD and the Deployment. Read the release notes first: the API is `v1alpha1` and may change.

## Uninstall

Delete the BackupPolicies first, while the operator is still running. Each policy has a finalizer that removes its Jobs, and a policy cannot finish deleting without the controller:

    kubectl delete backuppolicies --all --all-namespaces
    kubectl delete -f dist/install.yaml

Deleting the CRD deletes every remaining BackupPolicy. Backups already stored in the bucket are never deleted by uninstalling.
